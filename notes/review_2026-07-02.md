# Code review pass — 2026-07-02 (Fable 5)

A review of the codebase as it stood at commit `c070d6d` (all prior code written
in Opus sessions). Verdict: design and methodology were sound; all five fixes
below are about **reliability and time-series honesty**, not logic errors in the
signal itself. Uncommitted at time of writing — check `git log` for the commit.

## What changed and why

### 1. `hl/client.py` — leaderboard cache made corruption-proof (highest impact)
**Before:** the ~32MB download was written straight to `data/leaderboard.json`
with no validation. A truncated/failed download left corrupt JSON that the
freshness check (mtime) then treated as *fresh*, breaking every run — including
the hourly `whales_track.py` cron — for up to an hour.
**Now:** the download is `json.loads`-validated first, written to a `.tmp` file,
then atomically `rename`d over the cache. If the refresh fails and a stale cache
exists, it falls back to the stale cache with a warning on stderr (a stale
leaderboard is a fine ranking hint; a dead cron run is not). Only raises if
there is no cache at all.

### 2. `whales_coin.py` — fetch failures counted, not swallowed
**Before:** `scan_address` caught all exceptions and returned `None` — identical
to "scanned, not a whale". In a time series this made "fewer whales this hour"
indistinguishable from "the API errored more this hour".
**Now:** exceptions propagate out of `scan_address`; `scan_whales` counts them,
warns on stderr when any occur, and — new optional param — populates a caller
supplied `stats` dict with `n_scanned` / `n_failed`.
`scan_whales(hl, progress=False, stats=None)` is the new signature; existing
positional callers are unaffected.

### 3. `whales_track.py` — prediction test hardened
- **Snapshot schema:** each JSONL row now also carries `"n_failed"` (from the
  scan stats above), so a degraded snapshot can be identified after the fact.
  Rows written before 2026-07-02 lack the key — use `.get("n_failed", 0)`.
- **Spacing guard in `--analyze`:** horizon is measured in *steps*, which only
  equals a fixed timespan if snapshots are evenly spaced. Missed cron runs
  create 2–3h gaps whose forward returns aren't comparable to 1h ones. Analyze
  now computes the median inter-snapshot gap and drops (t, t+h) pairs outside
  0.5–1.5× the median, reporting how many were dropped. (On the first run it
  dropped 1 of 107 pairs.)
- **Base rate next to hit-rate:** `const-guess base=NN%` = the hit-rate of
  always guessing the majority sign. A signal hit-rate is only informative
  *above* this. First real reading (108 snapshots, h=1): BTC 54% vs base 54%,
  ETH 47% vs base 53%, ratio-spread 46% vs base 54% — **no edge at 1h horizon
  yet**. Worth re-testing with `HORIZON_STEPS` 4–24 once more data accumulates.
- **Crash fix:** the post-snapshot ratio print divided by `prices.get(b, 1)`,
  but a missing `markPx` puts a real `0.0` *in* the dict, so the default never
  applied → ZeroDivisionError in the cron. Now guards `if pb else 0.0`.

### 4. `btc_flows.py` — `--hours` no longer silently under-reports busy wallets
**Before:** movements mode read only `address_txs` (last ~50 txs) and filtered
by time. For Binance hot (2.26M txs) 50 txs can span mere hours, so a wide
`--hours` window silently missed older movements — while `--netflow` mode
already paginated correctly.
**Now:** new `_watch_txs` helper — with no window it keeps the old cheap
behavior (last ~50); with `--hours` it takes mempool (unconfirmed) txs plus
`_txs_since`-paginated confirmed history back to the window start. Same API
cost profile as netflow mode; the mempool.space throttling caveat in
notes/btc_onchain.md still applies to very wide windows.

### 5. `btc/arkham.py` — explicit `import urllib.error`
The `except urllib.error.HTTPError` handler previously worked only via the
side effect of `import urllib.request` importing `urllib.error`. Now imported
explicitly; the `# type: ignore` is gone.
